# work_streams

The work-item model, and the pieces every reader and writer of one shares.
[CONTRACT.md](CONTRACT.md) is the authority. Read it first, and read it before
adding a stream.

Two pieces of it are written up and not yet done:
[HANDOVER-improvements.md](HANDOVER-improvements.md) brings each repo's
`IMPROVEMENTS.md` in as the third stream, and
[HANDOVER-ui-extraction.md](HANDOVER-ui-extraction.md) moves the board's shared
rendering in here so a fourth queue does not mean a fourth view.

## Why this exists

Three things in `~/Code` are queues of work items moving through states: the
master to-do list, the night agent's plans, and each repo's `IMPROVEMENTS.md`.
They were built separately and shared nothing, so the same ideas were written
down several times over and drifted. Plan status alone was known in seven places
that had to be edited together. Identity was four incompatible schemes: an
optional slug, a per-parse id nothing outside the tab could use, task titles,
and a hash of an entry's body.

The cost of that is not tidiness. It is that a fourth agent means a fourth board
and a fifth copy of the vocabulary, which is the point at which this stops being
worth running.

So the model lives here once, the vocabulary lives here once, and a stream is
described by a manifest rather than by code that knows about it.

## What is in here, and what deliberately is not

The item, the six states, the lane arithmetic, the manifest reader, the two
container encodings, the transition router, and the card and column renderers.
Anything a second app would otherwise copy.

What is not here is any one stream's grammar. `todo.md`'s tags, its recurrence
rules and its working calendars stay in `to-dos/core/`, because exactly one app
parses that file, and `PACKAGES/README.md`'s own rule is that one app and a
library is just that app's code. What `to-dos/core/` gains is a projection into
the item above, and nothing else.

There is a second reason those two files stay where they are, and it is worth
knowing before anyone tries to move them. The board is deployed as a static site,
where it loads `/core/todo.js` by absolute path. That resolves only because the
file sits inside the deployed repo. Move it and the board does not degrade, it
stops. Nothing the board needs in order to start may come from this package, and
everything served from here has to survive a 404 the way the chat engine's
stylesheet already does.

## The classic-script rule

`interface/item.js`, `interface/lanes.js` and `interface/card.js` are classic
scripts. They must stay free of `window`, `document` and `state`, and they must
not become modules.

Both halves of that are load-bearing. The board loads them with plain script
tags before its own scripts and reads their names out of the shared global
scope, so a module would be deferred past the point where those names are first
needed and every one of them would be missing. And the test suite runs them in a
bare context with no browser in it, which is what makes them fast and unable to
touch anything.

`interface/board.js` needs the DOM, so it takes the element to draw into as an
argument rather than reaching for one. That keeps the rule true for everything
above it.

## How it is wired in

By relative path, like `ai_chat_engine` and unlike `graph-engine`.

Python consumers add this folder to their path, worked out from their own
location. The browser half is served by whichever app is serving the page, the
way `to-dos/kanban/server.py` already serves `/ai-chat/`.

The network route `graph-engine` uses is not available here. It needs a
`package.json` in the consumer, and the `to-dos` board has never had one or a
build step, which is a property worth keeping rather than trading away to reach
a folder two directories up on the same disk. Python could not use it either.

The price is the same as `ai_chat_engine`'s, minus its worst part. Moving this
folder means editing the path in each consumer. Nothing reaches it through npm,
so there is no symlink to relink, which is the failure that does not announce
itself.

## Testing

The arrangement is the one `to-dos/core/` already uses, because it works: JSON
tables generated by running the real functions, read by both a Python suite and
a JavaScript one, with neither suite holding a table of its own. A change to the
model therefore has to be expressed once, and shows up as a failure in both
languages if only one side was updated.

```
python3 test_streams.py     node test_streams.mjs
```
